# 异地同步观影室 — 实施方案 v3

> 目标：两个人异地、各自用手机看同一部片子，播放/暂停/进度完全同步，且**没有任何第三方能看到你们在看什么**。

**v3 修订说明**：她的实际位置是**加拿大**（不是国内）。v2 的 App Store 障碍消失，新增 §3.5「跨洋链路适配」，地基顺序调整为「公网直连 > Tailscale > WebRTC」。
**v2 修订说明**：v1 把"Tailscale 组网"当作地基，但**实测确认 Tailscale 的 iOS App 不在中国区 App Store 上架**（对照实验：`apps.apple.com/cn/.../wechat` 返回 200，`apps.apple.com/cn/.../tailscale` 返回 404）。因此新增 §3.0「地基三选一」，M0 相应重写。

---

## 0. 一句话结论

**电脑只当"文件服务器 + 时间轴服务器"，不播放、不解码、不转码；两台手机各自从电脑拉原始码率的 MP4 自己解码播放；同步靠一条 WebSocket 广播权威时间轴。**

前提是**先解决"她的 iPhone 怎么访问到你的电脑"**——这是本项目唯一的地基问题，见 §3.0。

## 1. 已确认的需求与约束

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 网络 | **中国 ⟷ 加拿大** | 跨洋链路质量是新的主要瓶颈（延迟 ~180–250ms，晚高峰拥塞/丢包） |
| 你的出口 | NAT 后（`192.168.1.100`），**无全局 IPv6** | 公网直连需先解决公网 IP |
| 她的位置 | **加拿大**，iPhone | 加拿大区 App Store 极可能有 Tailscale（美/新/越区页面均在，加区未直接验证，**让她搜一下确认**） |
| 片源 | MP4，1080p 及以下 | **基本不需要转码**，最理想情况 |
| 电脑 | Windows 11，可一直开机，Node 22.23.2 已装 | 服务器常驻可行，只需防睡眠 |
| 观看设备 | 你的安卓 + 她的 iPhone | iOS Safari 是主要兼容目标 |
| 聊天 | **不需要** | M4 去掉该项 |
| 隐私底线 | 内容不走第三方 | 拒绝任何 TLS 终止型代理（含 Cloudflare Tunnel） |

## 2. 架构（模式 A）

```
                    ┌─────────────────────────────────────┐
                    │  你的 Windows 电脑（常开，屏幕可关）  │
                    │                                     │
                    │  Node 服务 (HTTP + WebSocket)       │
                    │   ├─ HTTP: 网页 + 片库 API           │
                    │   ├─ HTTP: 视频文件 (Range 分片)     │
                    │   └─ WS  : 房间 + 权威时间轴         │
                    └──────────────┬──────────────────────┘
                                   │  加密通道（见 §3.0 三选一）
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
          [你的安卓 · Chrome]            [她的 iPhone · Safari]
          拉原始码率 → 本地解码           拉原始码率 → 本地解码
          上报/接收时间轴                  上报/接收时间轴
```

**电脑不参与解码**，只维护一个纯数学的虚拟时钟。

### 为什么不用"电脑推流 + WebRTC"

| 维度 | 模式 A（本方案：文件服务器） | 模式 B（WebRTC 推流） |
|---|---|---|
| 画质 | 原始码率，无损 | 实时重编码，有损 |
| 电脑 CPU | ≈ 0 | 2 路编码，高负载 |
| 电脑前台 | 不需要 | **必须**（后台标签页被节流） |
| 上行带宽 | 2 × 原始码率 | 2 × 重编码码率 |
| 同步精度 | 高（无接收缓冲差异） | 差（各自缓冲 0.5–2s 不等） |
| 对 iOS 的要求 | 需能访问到 PC | 只收媒体流，零安装 |

模式 B 唯一优势是"不依赖任何组网"，**如果 §3.0 三条地基全部走不通，它就是兜底方案**。

## 3. 关键技术决策与依据

### 3.0 地基选型 ⚠️ 本项目最大的不确定性

**新情况：对方在境外。** App Store 问题消失（加拿大区正常上架 Tailscale），但瓶颈换成**中加跨洋链路**。

#### 中国这边用 Tailscale 的三个已知问题（均有实证）

| 问题 | 表现 | 来源 |
|---|---|---|
| UDP 打洞被劣化 | 联通/移动下直连打洞被"严重人为劣化"，退化为中继 | [V2EX 实测帖](https://global.v2ex.co/t/1222087) |
| DERP 中继绕道太平洋 | 默认中继路线从中国绕太平洋，延迟高，需自建港/日中继 | [知乎：给 Tailscale 装一台"自己的"HK 中继](https://zhuanlan.zhihu.com/p/2049105946681545694) |
| 控制面被 ISP 干扰 | 部分 ISP 静默丢弃带 ML-KEM 的 ClientHello，控制面连不上 | [tailscale#20777](https://github.com/tailscale/tailscale/issues/20777) |

结论：**Tailscale 能用，但在中国这边可能需要自建港/日 DERP 中继（VPS 约 ¥20–40/月）才能拿到可接受的跨洋延迟。**

#### 地基 ①：公网直连 + 免费域名 + Let's Encrypt —— 单对单场景最干净（推荐先试）

- 她**零安装**，只点一个 `https://` 链接；TLS 在你 PC 上终止，**路径上没有任何第三方**
- 不需要 VPS，不依赖 Tailscale 控制面，只有一条中国 ⟷ 加拿大的直连 TCP
- 前提：家宽有**公网 IPv4**（可能需打运营商电话申请）或**公网 IPv6**（你机器现在没有，需去小米路由器后台开启并确认运营商下发）
- 证书：Let's Encrypt 走 **DNS-01**，不需要开放 80 端口做校验
- 域名：DuckDNS 等免费 DDNS 子域配合 DNS-01 即可，**成本 ¥0**；想稳一点买域名约 ¥60–100/年
- ⚠️ 边界提示：用域名 + 国内家宽对外提供服务，严格说涉及备案；个人自用 + 非标准端口在实践中常见，但你要知道这条线

#### 地基 ②：Tailscale +（按需）自建港/日中继

- 对方在境外区 App Store 直接装，技术成熟、免费、自动证书
- 中国这边的三个问题见上表；若打洞成功且延迟可接受，到此为止
- 若退化为绕太平洋中继 → 自建 DERP，内容仍是端到端加密，中继只见密文
- 官方路线，最省心，但在中国的可用性**必须实测**

#### 地基 ③：WebRTC 推流 + 二维码 —— 零安装零成本，但体验降级

- 不需要公网 IP、不需要域名、她只用 Safari 扫码
- 代价：**模式 B 的全部缺点**（画质有损、PC 需前台不被节流、开发量 3–5 倍）
- 跨洋 WebRTC 同样受链路质量影响，打洞失败还需 TURN 中继（要 VPS）
- 仅前两条都不通时考虑

#### 上游问题：对方在境外有没有电脑？

如果有（Mac 或 Windows），一切都变简单：

- 桌面端不受 App Store 限制，Tailscale 直接可装
- 桌面端没有 iOS 的任何限制（格式、锁屏断连、后台节流全都不存在）
- **强烈建议至少"她"这一端优先用电脑**，iPhone 只作为备选

### 3.5 跨洋链路适配（针对中国 ⟷ 加拿大）

- **带宽方向对我们有利**：只有**她一路**跨洋（你在家走局域网，不占国际出口）。1080p 8 Mbps 单路，比"两人都跨洋"好得多
- **延迟**：典型 RTT 180–250ms。对同步本身几乎无影响（时间轴广播只有几十字节），但对 **seek 体验**影响明显——每次 seek 都要重新跨洋拉数据，她那边可能等 2–10 秒
- **晚高峰**：中国国际出口在北京时间 20:00–24:00 最拥塞（加拿大是早上）。**建议实测不同时段速率**，必要时把看片时间挪到中国白天
- **两个针对性设计**：
  1. **开局大缓冲**：她的客户端先缓冲 20–60 秒再 3-2-1 开始（阈值可配），用缓冲换稳定，避免晚高峰抖动打断
  2. **可选预缓存**：客户端支持"先下载完再看"——她有空时提前把片子拉到本地，观看时完全走本地，**同步精度最高、完全不受链路影响**。这可能是你们跨洋场景的日常用法

### 3.1 传输：HTTP Range 直传，不转码

- 必须支持 HTTP Range 请求（iOS Safari 拖进度条完全依赖它）与 `HEAD` 请求
- 必须返回 `Accept-Ranges: bytes`、`Content-Range`、`206 Partial Content`
- 使用 `express.static`（底层 `send` 已实现条件请求与 Range）；若 iOS 出现异常则手写 Range 处理器（约 40 行）
- 文件在服务器上只有一份，**两台手机拉到的必然是同一个文件**——"双方片源版本不一致"这类同步难题在模式 A 里天然不存在

### 3.2 为什么必须 HTTPS

`http://192.168.x.x` **不是**安全上下文（只有 `localhost` 例外），会导致：

- `navigator.wakeLock`（防息屏）不可用
- 部分媒体/权限 API 受限，自动播放策略更严

三种地基都能满足：

| 地基 | 如何拿到可信 HTTPS |
|---|---|
| ① Tailscale | `tailscale serve` 自动签发证书 |
| ② 公网直连 | Let's Encrypt（DNS-01），PC 上 Node 直接加载证书 |
| ③ WebRTC | 不需要——媒体流本身由 DTLS-SRTP 加密 |

### 3.3 同步算法（本项目真正的技术核心）

#### 权威模型

服务器持有唯一权威状态：

```
RoomState { mediaId, playing, anchorPos, anchorServerMs, rate }
```

不变式：`playing` 时，任意服务器时刻 `t` 的期望播放位置为

```
targetPos(t) = anchorPos + (t - anchorServerMs) / 1000
```

任何客户端操作（play / pause / seek）**只上报意图**，由服务器更新 `anchor` 并广播，所有客户端（含发起者）一律以广播为准。这样双人同时操作不会打架（最后到达者生效）。

#### 时钟偏移估计

- 客户端定期 `ping`，服务器 `pong` 带回服务器时间戳
- 按 NTP/Cristian 算法取偏移：`offset = ((t1-t0) + (t2-t3)) / 2`
- 取最近 N 次中 **RTT 最小**的样本作为最终估计（避免网络抖动污染）
- 之后 `serverNow ≈ localNow + offset`

#### 校正策略：桌面/安卓 与 iOS 必须分叉 ⚠️

**关键坑**：iOS Safari 在播放中修改 `playbackRate` 会造成 **80–300ms 的音画卡顿**，WebKit 上该 bug 2016 年报告，**至今状态仍是 `NEW`**，2025 年 6 月仍有开发者因它无法实现多设备同步播放而抱怨（[WebKit #163433](https://bugs.webkit.org/show_bug.cgi?id=163433)）。

教科书式的"微调播放速率悄悄追平"在 iPhone 上会变成每隔几秒卡一下。因此：

| 平台 | 策略 |
|---|---|
| 桌面 Chrome / 安卓 Chrome | **rate nudging**：`60ms ≤ |drift| < 800ms` 时 `rate = clamp(1 - drift*k, 0.96, 1.04)`，收敛后回 1.0 |
| **iOS Safari** | **禁用 rate nudging**，改用"惰性 seek 校正"（见下） |
| 所有平台 | `|drift| < 60ms` 一律不动；首次对齐与 seek 后一律硬 seek（用户已预期跳变） |

**iOS 惰性 seek 校正**（为什么这样够用）：

- 设备晶振差异约 10–100 ppm → 每分钟漂移仅 0.6–6 ms → 一部 2 小时电影累计漂移约 **0.07–0.7 秒**
- 所以**不需要连续微调**，低频校正就够：
  - 仅当 `|drift| ≥ 200ms` **且**距上次校正 ≥ 120s 时，做一次精确定位
  - 暂停状态下只要 `|drift| ≥ 60ms` 就立即校正（暂停时定位零成本、零听感影响）
  - 优先把校正机会"攒"到暂停/缓冲时刻用掉

#### 防跳音与操作细节

- 拖动进度条时先发 `seeking`（仅本地预览，不广播），**松手才发 `seek-commit`**，避免对端被连续 seek 打断
- 禁止重复写入相同的 `playbackRate` 值
- 校正尽量避开"正在播放且有声音"的时刻

#### 缓冲与就绪握手

- 任何客户端进入 `waiting` / `stalled` → 上报 → 服务器广播"全员暂停等待"
- 双方都 `canplay` 且缓冲 ≥ 3s → 服务器广播 3-2-1 倒数，倒数结束时把 `anchor` 设为当前时刻

#### 断线与前台恢复

- WS 心跳 5s，断线指数退避重连（1s → 2s → 4s … 上限 15s）
- `visibilitychange` 回到前台 → **不信本地 `currentTime`**，重新拉服务器状态并用时间戳重算目标位置
- iOS 锁屏必然断连（平台限制），恢复时按"重新入场"处理：不弹就绪握手，直接定位
- 播放期间用 Screen Wake Lock 尽量维持亮屏

### 3.4 访问控制

- 地基 ① 下可用 Tailscale 注入的 `Tailscale-User-Login` 头做白名单
- 地基 ②③④ 下用配置文件里的 PIN（首次进入房间时输入一次，存 localStorage）
- **不端口转发到公网时也要设 PIN**——地基 ② 下服务是公网可达的

## 6. 里程碑与验收标准

### M0 — 地基选型验证（你操作，10–30 分钟，无需写代码）

**必须先做，且只需回答两个问题：**

**问题 1：她手机上能不能装到组网工具？**（10 秒）
让她在 App Store 搜 `Tailscale`。同时确认她有没有**非中国区 Apple ID**。

**问题 2：你家宽带有没有公网 IP？**（5 分钟）
```powershell
(Invoke-RestMethod https://ifconfig.me/ip)   # 你出口的公网 IPv4
(Invoke-RestMethod https://api64.ipify.org)  # 若返回 IPv6 说明有 IPv6 出口
```
再打开小米路由器后台，看**上网设置里的 WAN IP**：

| 现象 | 含义 |
|---|---|
| WAN IP == 上面查到的公网 IP | ✅ 有公网 IPv4，地基 ② 可行 |
| WAN IP 是 `100.64.x.x` / `10.x.x.x` | ❌ 运营商级 NAT（CGNAT），需打运营商电话申请公网 IP |
| 查到的 IPv6 以 `2` 或 `240e` 开头 | ✅ 有公网 IPv6，地基 ② 可行（路由器需放行入站） |

**还有一个上游问题**：对方有没有 Windows 电脑？如果有，地基问题**直接消失**——两台电脑之间可以直接用现成的虚拟局域网工具，且没有 iOS 的任何限制（格式、锁屏断连全部不存在）。

**决策表**：

| 情况 | 选地基 |
|---|---|
| 有公网 IPv4 或 IPv6 | **地基 ①**（免费域名 + Let's Encrypt，她零安装，¥0） |
| 没有公网 IP，但 Tailscale 直连打洞成功 | **地基 ②**（Tailscale，她装一次） |
| Tailscale 退化为绕太平洋中继 | 地基 ② + 自建港/日中继（¥20–40/月） |
| 她有电脑 | 优先让她用电脑端（绕开所有 iOS 限制） |
| 以上都不行 | 地基 ③（WebRTC 推流 + 二维码，体验降级） |

### M1 — 服务器骨架（token 8–15 万）
Node 服务 + 片库扫描 API + Range 视频服务 + 最小播放页。
**验收**：同 WiFi 下手机浏览器打开页面，看到片库，选中 MP4 播放，能拖进度条、能切换视频（此时还没同步）。
**注**：M1 **不依赖 M0**，可以在局域网里先开发调试，与 M0 并行。

### M2 — 同步核心（token 15–25 万）
WS 房间、权威状态机、时钟偏移估计、双向同步、分叉校正策略。
**验收**：一头暂停/播放/拖动，另一头 1 秒内跟随；稳态偏差中位数 < 150ms；**iOS 端全程无可听见的卡顿**。

### M3 — 健壮性（token 8–15 万）
就绪握手、等待缓冲、3-2-1 倒数、断线重连、前台恢复重校准、Wake Lock。
**验收**：拔网 10 秒恢复后自动对齐；一方缓冲不足时双方一起等；iPhone 锁屏再解锁自动回到同一位置。

### M4 — 体验（token 10–20 万，可选）
片库 UI（时长/搜索）、外挂字幕同步、连播、Windows 一键启动 + 防睡眠脚本、二维码页（地基 ③ 必需）。
**验收**：她全程不需要打开命令行。

| 6 | 家宽上行不足 | 画质被迫降级 | 1080p 8 Mbps × 2 = 16 Mbps | M0 实测；必要时降码率 |
| 7 | iOS seek 精度与重新缓冲 | 校正瞬间可能短暂停顿 | 已知行为 | 校正频率低（≥120s）+ 优先暂停时校正 |
| 8 | 地基 ② 下服务公网可达 | 陌生人扫到端口 | — | PIN + 非标准端口 + 失败限速 |
| 9 | 片源含 DTS/AC3 音轨或 moov 在文件尾 | iOS 播放异常 | 常见于某些压制组 | `mp4.js` 检测并提示；备用 remux 脚本 |
| 10 | PC 走 WLAN 而非有线 | 长时间高码率上传稳定性 | 已确认是 WLAN | 建议串流期间插网线 |

- **hev1 传输改写**：原方案要求用户跑 ffmpeg 或修改盘上文件才能让 iPhone 播放 HEVC。
  改为服务端在发送字节时改写 sample entry 的 4 字节 fourcc，**硬盘原文件零改动**，且因长度不变，

### 屏幕共享（已实现）

`src/rtc.js` 做信令中转，`public/screen-share.js` 做采集与接收。

- 共享端 `getDisplayMedia` 采集 → 给房间里每个观看者各建一条 WebRTC 连接
- 观看端只需 `RTCPeerConnection`，渲染到全屏层（右下角有全屏按钮）
- **画面走 P2P，服务端只转发 SDP/ICE，完全不接触画面**
- 共享者断开时房间状态自动清掉，不会让人干等
- 入口在页面右上角「控制台」旁边，**始终显示**；不可用时边框变虚线并说明原因
  （静默隐藏会让人以为功能不存在 —— 之前就是这么被误解的）
- 目标 **60 帧**：`getDisplayMedia` 的 `frameRate` 约束只管采集，还要在 sender 上
  显式声明 `maxFramerate`，否则编码器会自行压到 30
- 带宽不足时默认 **保分辨率**（`maintain-resolution`）：共享屏幕是看内容，糊掉就失去意义。
  代价是帧率会掉，可通过 `rtc.degradationPreference` 改回 `maintain-framerate`
- **声音**：`getDisplayMedia({ audio: true })` 连系统声音一起采。
  观看端默认静音（自动播放策略所限），点「观看」时在该手势内解除静音，
  并提供「开启声音 / 静音」开关。共享端自己的预览恒静音以避免啸叫。
  Windows 上必须选「整个屏幕」并勾选「分享系统音频」，否则只有画面没有声音且不报错。

**实测的浏览器能力边界**（`tools/check-browser-caps.js`）：

| 地址 | 安全上下文 | 采集屏幕 | 接收画面 |
|---|---|---|---|
| `http://127.0.0.1:8080` | ✅ | ✅ | ✅ |
| `http://192.168.1.100:8080` | ❌ | ❌ | ✅ |

所以采集端目前只能"在电脑上用 localhost 打开"。**这也是 HTTPS 的第二个实际收益**
（第一个是让她 iPhone 拿到 Wake Lock，否则屏幕会自动熄灭中断播放）。

验证：`tools/test-screen-share.js` **36/36 通过**。用 canvas 动画流 + WebAudio 音频轨注入
代替真实采集，覆盖：信令转发 → WebRTC 建连 → 观看端收到画面与声音（画面持续更新、
音频轨活跃）→ 第三台设备自动接入 → 60 帧稳态 → 全屏入口 → 静音开关 → 结束与断开收尾，
以及**真实拓扑**（电脑从 `127.0.0.1` 共享、手机从局域网 IP 观看，跨源 P2P 打通）。
唯一没覆盖的是"点系统弹窗选屏幕并勾选分享音频"那一步。

### 修掉一个真实的 UX 疏漏

共享提示条原先放在播放页内部，导致手机上**没先选一部片子就完全看不到有人在共享**。
现在提示条是全局的（在顶栏下方），片库页也能看到；共享按钮也移到了右上角，
不必先选片就能开始共享。测试里加了断言守住：手机停在片库页时必须能看到提示条与「观看」按钮。

跨洋直连需要能打通 NAT；`config.json` 的 `rtc.iceServers` 默认是**空**的 ——
刻意不配任何第三方 STUN，以维持"内容不经过第三方"这个性质。

### 修掉一个无限递归

屏幕共享首次接入时，`updateSharing → syncPeers → onStatus → updateSharing` 形成闭环，
浏览器报了一堆 `Maximum call stack size exceeded`。功能表面还能用，但控制台全是错误。

修法两层：`onStatus` 只刷新提示条文字，绝不再回头调用 `updateSharing`；
同时用"对端集合指纹"避免每次状态广播都重建一遍 WebRTC 连接。

### 并发能力（实测数据）

片源平均码率 **5.4 Mbps**，所以并发上限完全由上行带宽决定（服务端 CPU 几乎不随人数增长）：

| 上行 | 理论上限 | 建议 |
|---|---|---|
| 20 Mbps | 3 路 | 2 路 |
| 30 Mbps | 5 路 | 4 路 |
| 50 Mbps | 9 路 | 8 路 |

**局域网内的设备不占上行** —— 所以他本人在家看时，"你 + 她"只消耗 **1 路 ≈ 5.4 Mbps**，
上表应理解为"异地观看端"的数量。

### 运行形态与控制台（已解决）

服务是 Node 进程，默认不会随电脑启动。已提供：

- `tools/start-hidden.vbs` —— 无窗口后台启动，日志写 `data\server.log`
- `tools/stop-server.ps1` —— 停止（读 `data\server.pid`，也支持按命令行兜底匹配）
- `tools/install-autostart.ps1` —— 注册 / 查看 / 移除开机自启；
  默认「登录时启动」（免管理员），可切 `-Mode Boot`（以 SYSTEM 运行，无需登录）
- `tools/set-pin.ps1` —— 改访问码并重启
- **`/admin.html` 网页控制台** —— 状态、访问码、片库、访问地址、开机自启、播完关机、
  观看断点、日志，全部在浏览器里完成（手机也可用）

已实际注册并验证：任务 `\VideoWatcher`，`Schedule Type: At logon time`，
`Task To Run: wscript.exe ...\tools\start-hidden.vbs`，停止/重启循环均正常。

### 修掉一个会让整个服务崩溃的问题

`tools/test-admin-api.js` 第一次运行时**把服务打崩了**（ECONNRESET）。根因有两层：

1. **Express 4 不捕获 async 路由抛出的异常** → 变成未处理的 Promise rejection →
   Node 15+ 默认**终止进程**。也就是说管理接口里任何一个意外异常，
   都能在你们正看片的时候把整个服务打死。
   修法：新增 `src/async-handler.js`，所有 async 路由用它包一层；
   补上 Express 错误中间件，以及 `unhandledRejection` / `uncaughtException` 保命日志。
2. `execFile` 在受限环境下会**同步抛出** `spawn EPERM`（无法创建管道），
   这个同步异常不会被 Promise 捕获，直接终止进程。
   控制台的开机自启功能依赖它，现在会兜住并返回明确的替代方案提示。

测试里专门留了一条断言守住这个回归：**"接口报错后服务仍然存活"**。

## 13. 第三方网站同步播放（bilibili 等）—— 可行性分析

### 做不到的那一种：「输入网址就能在程序里播放」

- 网站播放器是**跨源隔离**的。把 bilibili 播放器嵌进 iframe 后，我们的页面
  **无法读取或设置它的播放位置**，官方也没有提供第三方时间轴控制接口。
- 另一条路是让服务端去解析真实视频流地址再转发给你们。这需要绕过它们的
  防盗链签名，等于把对方的内容经我们的服务器二次分发 ——
  既违反服务条款，又要持续对抗反爬，且带宽全部压在这台电脑上。**不做。**

### 可以做到的那一种：用户脚本只同步"时间轴"

两个人各自在浏览器里打开同一个 bilibili 视频，用一个用户脚本
（Tampermonkey）挂到页面自己的 `<video>` 元素上：

- 读取该元素的 `currentTime` / 播放状态，上报给我们的服务端
- 接收服务端的权威时间轴，对同一个元素执行 play / pause / seek

内容仍然由 bilibili 各自发给各自，我们只传递几十字节的同步消息，
**服务端不接触也不转发任何视频数据**。

### 但有三件事要先想清楚

1. **这打破了本项目最初的核心目标。** bilibili 就是平台方，它完全能看到
   你们各自看了什么、什么时候看的。本地片源那套"内容不经第三方"的保证
   在这里**不成立** —— 这不是实现问题，是模式本身的属性。
2. **对方在境外。** 大量 bilibili 内容有地区限制，她可能根本打不开。
   这个问题会比"同步"更早暴露。
3. **双方都要装东西。** 你在电脑/安卓上装 Tampermonkey 很简单；
   她 iPhone 上要装能跑用户脚本的 App（如 Stay / Userscripts），
   麻烦且不稳定 —— 这跟之前排除了 Tailscale 中国区不可用是同一类障碍。

### 如果要做，我会怎么落地

1. 服务端加"外部媒体"支持：房间的媒体标识从片库条目扩展为任意 URL，
   状态里带上 `external: { url, title }`
2. 写用户脚本：连 WebSocket、上报位置、应用权威时间轴；
   选择器做成可配置，以应对站点改版
3. **验证方式**：写一个本地 mock 页面（就是普通的 HTML + `<video>`），
   把用户脚本挂上去跑真实的双臂同步测试 —— 这样协议层是**可验证**的，
   唯一无法在这里验证的只有 bilibili 的具体 DOM 结构
4. 先只在你电脑上跑通，确认可用后再考虑她的 iPhone

| 桌面端偏差 | 中位数 -37 ~ -60ms，p90 39 ~ 238ms |
| iOS 路径偏差 | 中位数 -107 ~ +141ms，p90 109 ~ 168ms |
| iOS 端 playbackRate | 6 次采样恒为 **1**（证实从不改速率） |
| 暂停同步 | 相差 **0.00s** |
| 自适应前置缓冲 | 实测 347 Mbps → 需求降到 **5s** |
| 页面 JS 运行时错误 | **0** |

**为什么会有 100–200ms 的跨设备差异**：这是 iOS 惰性校正策略的固有代价。iOS 端不做
速率微调，只在偏差超过 `thresholdMs`（200ms）且距上次校正超过 120 秒时才 seek 一次，
所以它会"停在哪儿就是哪儿"。桌面端则用 rate nudging 平滑收敛到目标附近。

这个取舍是有意的：200ms 对"两个人在不同国家一起看片、边看边聊"完全无感，
而频繁 seek 在 iOS 上每次都会带来可见的卡顿（WebKit #163433）。

> **两个测量层面的坑（都已修）**：
> 1. 早期用 `video.currentTime` 统计偏差 —— 浏览器约每 250ms 才更新一次它，
>    自带 ±125ms 量化噪声，曾把真实 20ms 的偏差测成 400ms。
>    改用 `requestVideoFrameCallback` 的帧呈现时间后才可信。
> 2. 跨设备位置差曾经用墙钟补偿采样间隔，但系数算错一倍，导致结果随采样耗时剧烈波动。
>    正确做法不需要补偿：两端偏差本就在同一服务器时间轴上测得，"偏差之差"即位置差。

这不能替代真机验收（真实 iOS 的播放器行为和跨洋链路只有实测才知道），
但它把"客户端代码从未被执行过"这个风险清掉了。
